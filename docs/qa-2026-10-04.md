## Limits and required live checks

The headless diagnostic boot used a temporary serial-console variant and local
OVMF with Secure Boot disabled. It validates executable startup and rejection
on an unsupported machine; it establishes **no** Azure, Secure Boot or workload
attestation acceptance. These test artifacts and signing keys are not release
trust material. Kernel module-signature enforcement and lockdown remained
enabled; no production verification bypass was added.

Live Azure TDX evidence, custom UEFI enrollment, Hyper-V networking and DHCP
renewal, the vendor-qualified firmware/boot profile, both upstream providers and
multi-account load behavior still require a development Azure VM. The required
acceptance and rejection cases are in the [qualification runbook](azure.md).
The gateway intentionally cannot serve inference until those trust inputs pass
fresh local verification and backend admission.
